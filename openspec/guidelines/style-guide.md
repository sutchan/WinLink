# WinLink 项目文档风格指南

## 概述

本风格指南旨在为 WinLink 项目的文档编写提供统一的规范和标准，确保所有文档具有一致的风格、格式和质量。遵循本指南可以提高文档的可读性、可维护性和专业性。

## 文档结构

### 基本结构

所有文档应遵循以下基本结构：

1. **标题**：文档的主标题，清晰描述文档内容
2. **描述**：文档的简要描述，包括目的和重要性
3. **主要内容**：根据文档类型组织的详细内容
4. **参考资料**：相关的参考链接和资源
5. **变更历史**：文档的修改记录

### 标题层级

使用 Markdown 标题层级组织文档结构：

- `#`：一级标题（文档主标题）
- `##`：二级标题（主要章节）
- `###`：三级标题（子章节）
- `####`：四级标题（详细子章节）

### 章节顺序

文档章节应按照逻辑顺序组织：

1. 概述/描述
2. 功能需求/核心概念
3. 技术实现/实施指南
4. 测试策略/监控审计
5. 常见问题/最佳实践
6. 参考资料
7. 变更历史

## 写作风格

### 语言选择

- **默认语言**：中文简体
- **英文使用**：技术术语、API 名称、代码等应使用英文
- **双语文档**：重要文档应提供中英文双语版本

### 语气和风格

- **专业客观**：使用专业、客观的语言，避免主观情感表达
- **清晰简洁**：表达清晰，语言简洁，避免冗长和复杂的句子结构
- **准确具体**：提供准确、具体的信息，避免模糊和笼统的描述
- **一致连贯**：保持文档风格的一致性和内容的连贯性

### 人称使用

- **第三人称**：技术文档应使用第三人称，避免使用第一人称（"我"、"我们"）
- **第二人称**：指南和教程可以使用第二人称（"你"、"您"），但应保持一致

### 时态使用

- **现在时**：描述当前的功能、特性和实现
- **将来时**：描述计划中的功能和改进
- **过去时**：描述已完成的变更和历史

## 格式规范

### 文本格式

- **加粗**：使用 `**` 标记重要概念、术语和标题
- **斜体**：使用 `*` 标记强调和引用
- **代码**：使用 `` ` `` 标记内联代码和命令
- **代码块**：使用
  ```
  标记代码块，并指定语言
  ```

### 列表格式

- **无序列表**：使用 `-` 或 `*` 标记，用于并列的项目
- **有序列表**：使用数字标记，用于有顺序的步骤或流程
- **嵌套列表**：使用缩进创建嵌套列表，最多嵌套三层

### 表格格式

- 使用 Markdown 表格语法创建表格
- 表格应有清晰的表头
- 表格内容应对齐
- 复杂表格应考虑使用更合适的格式

### 链接格式

- **内部链接**：使用相对路径链接到项目内的其他文档
- **外部链接**：提供完整的 URL，并添加描述性文本
- **锚点链接**：使用锚点链接到文档内的特定部分

### 图片格式

- **图片路径**：使用相对路径或 URL
- **图片描述**：为图片添加描述性的 alt 文本
- **图片大小**：根据需要调整图片大小
- **图片质量**：确保图片清晰可读

## 内容规范

### 术语使用

- **术语一致性**：在整个文档中使用一致的术语
- **术语定义**：首次使用专业术语时应提供定义
- **术语表**：对于复杂文档，应提供术语表

### 技术准确性

- **代码示例**：确保代码示例语法正确、可执行
- **API 描述**：准确描述 API 的参数、返回值和使用方法
- **技术细节**：提供准确的技术实现细节和配置信息

### 可读性

- **段落长度**：保持段落简短，每段不超过 5-6 行
- **句子长度**：保持句子简洁，每句不超过 20-25 个单词
- **段落间距**：使用空行分隔段落，提高可读性
- **标题使用**：使用标题和子标题组织内容，提高文档结构清晰度

### 完整性

- **覆盖所有内容**：确保文档覆盖所有相关的内容和场景
- **避免遗漏**：检查并确保没有遗漏重要的信息和步骤
- **保持更新**：定期更新文档，确保内容与实际情况一致

## 特定文档类型的规范

### 功能规范文档

- **详细描述**：提供功能的详细描述，包括用户场景和使用流程
- **核心功能**：明确列出核心功能点，包括输入、输出和流程
- **技术实现**：描述技术实现细节，包括架构设计和数据模型
- **测试策略**：提供测试用例和测试方法

### 专题文档

- **核心概念**：清晰解释相关的核心概念
- **实施指南**：提供详细的实施步骤和最佳实践
- **技术实现**：描述技术实现细节和代码示例
- **常见问题**：提供常见问题和解决方案

### 变更提案文档

- **变更背景**：清晰描述变更的背景和原因
- **变更内容**：详细描述变更的内容和技术方案
- **变更影响**：分析变更的正面影响和潜在风险
- **实施计划**：提供详细的实施步骤和时间安排

## 代码示例规范

### 代码格式

- **语法高亮**：使用代码块并指定语言，启用语法高亮
- **缩进**：使用 2 或 4 个空格进行缩进，保持一致
- **行长度**：代码行长度不超过 80-100 个字符
- **注释**：添加必要的注释，解释复杂的代码逻辑

### 代码质量

- **可执行性**：确保代码示例可以直接复制执行
- **简洁性**：代码示例应简洁明了，专注于演示核心功能
- **完整性**：代码示例应包含必要的导入和初始化代码
- **注释**：添加适当的注释，解释代码的功能和使用方法

### 语言规范

- **TypeScript**：使用 TypeScript 编写前端代码示例
- **JavaScript**：如需兼容，可提供 JavaScript 版本的代码示例
- **Shell 命令**：使用 PowerShell 命令（Windows 环境）
- **配置文件**：提供完整的配置文件示例

## 质量保证

### 文档审查

- **自我审查**：编写文档后进行自我审查，检查语法、格式和内容
- **同行审查**：邀请团队成员审查文档，提供反馈和建议
- **专业审查**：对于重要文档，邀请相关领域专家进行审查

### 检查清单

文档发布前应检查以下项目：

- [ ] 文档结构完整，符合基本结构要求
- [ ] 标题层级清晰，逻辑顺序合理
- [ ] 语言表达清晰，语法正确
- [ ] 代码示例语法正确，可执行
- [ ] 链接和引用有效
- [ ] 格式一致，符合风格指南
- [ ] 内容准确，与实际情况一致
- [ ] 可读性良好，易于理解

### 常见错误

避免以下常见的文档错误：

- **拼写错误**：使用拼写检查工具检查拼写
- **语法错误**：确保语法正确，句子结构合理
- **格式错误**：确保格式一致，符合 Markdown 语法
- **内容过时**：定期更新文档，确保内容与实际情况一致
- **链接失效**：定期检查并更新链接
- **术语不一致**：确保术语使用一致

## 最佳实践

### 写作技巧

- **先大纲后内容**：先创建文档大纲，再填充详细内容
- **分层思考**：从整体到细节，逐层组织文档内容
- **用户视角**：从读者的角度思考，确保文档易于理解和使用
- **定期更新**：定期审查和更新文档，确保内容与实际情况一致

### 格式技巧

- **使用模板**：使用项目提供的文档模板，确保格式一致
- **统一风格**：遵循本风格指南，保持风格一致
- **适当使用视觉元素**：使用表格、列表、代码块等视觉元素提高可读性
- **保持简洁**：使用简洁的语言和格式，避免冗长和复杂的表达

### 维护技巧

- **版本控制**：使用 Git 进行文档版本控制
- **变更记录**：记录文档的变更历史，便于追踪和审查
- **反馈收集**：收集用户反馈，持续改进文档质量
- **团队协作**：鼓励团队成员参与文档编写和改进
