# 测试规范

## 描述

测试规范定义了 WinLink 项目的测试策略、测试用例设计、测试执行流程和测试覆盖率目标。它确保项目的质量和可靠性，防止回归问题，并为开发团队提供快速反馈机制。

> 当前状态：仓库 `package.json` 已声明 `test` 脚本并包含 `vitest`、`@testing-library/react` 等开发依赖，但**尚未编写任何测试文件**。本规范为目标规划，落地以实际代码为准。

## 测试策略

### 测试层次

1. **单元测试**
   - 测试独立的函数、组件和模块
   - 隔离测试，模拟外部依赖
   - 关注代码的最小可测试单元

2. **集成测试**
   - 测试模块间的交互
   - 测试服务层与外部系统的集成
   - 关注系统各部分如何协同工作

3. **端到端测试**
   - 测试完整的用户流程
   - 从用户视角测试应用程序
   - 关注实际用户场景

### 测试覆盖率目标

- **单元测试覆盖率**: 80% 以上（目标）
- **集成测试覆盖率**: 70% 以上（目标）
- **端到端测试覆盖率**: 覆盖核心用户流程

## 测试框架和工具

## 测试用例设计

### 设计原则

- **基于需求**: 测试用例应基于功能需求和用户故事
- **边界条件**: 测试边界值和异常情况
- **可重复性**: 测试应可重复执行，结果一致
- **独立性**: 测试用例之间应相互独立
- **清晰性**: 测试用例应易于理解和维护

### 核心功能测试用例

#### 磁盘管理测试（目标，基于实际 disk-scan 功能）

- **测试场景**: 扫描系统磁盘
  - **WHEN** 应用程序启动并扫描 C 盘程序目录
  - **THEN** 应返回应用文件夹列表
  - **AND** 每个对象应包含 id、name、sourcePath、size、status 字段

- **测试场景**: 应用程序排序
  - **WHEN** 用户按大小对应用程序排序
  - **THEN** 应用程序列表应按大小排序
  - **AND** 排序结果应符合预期

#### AI 安全分析测试（基于实际 geminiService 离线分析）

- **测试场景**: 分析启动
  - **WHEN** 用户点击 "Analyze Safety" 按钮
  - **THEN** 应调用分析服务
  - **AND** 应用程序状态应更新为 "Analyzing"

- **测试场景**: 分析结果处理
  - **WHEN** 离线规则分析完成
  - **THEN** 应给出风险等级与安全评分
  - **AND** 应更新应用程序对象的 safetyScore 和 aiAnalysis 字段

- **测试场景**: 系统关键路径判定
  - **WHEN** 分析命中 Windows/System32 等路径
  - **THEN** 风险等级应为 "high"

#### 应用程序迁移测试（基于实际 migrationService 模拟实现）

- **测试场景**: 迁移启动
  - **WHEN** 用户启动迁移过程
  - **THEN** 应调用 migrationService 的迁移方法
  - **AND** 应用程序状态应更新为 "Moving"

- **测试场景**: 迁移步骤执行
  - **WHEN** 执行迁移步骤
  - **THEN** 应按顺序推进 Idle → MKDIR → Robocopy → MKLINK → Completed
  - **AND** 每个步骤应正确更新迁移状态

- **测试场景**: 迁移取消
  - **WHEN** 用户取消迁移
  - **THEN** 应通过 AbortController 中止流程

#### 国际化测试（基于实际 translations.ts）

- **测试场景**: 语言切换
  - **WHEN** 用户更改语言设置
  - **THEN** 界面文本应更新为选定的语言

- **测试场景**: 文本翻译
  - **WHEN** 渲染 UI 元素
  - **THEN** 应使用 translations.ts 中正确的翻译文本

> 注：原规范提及的 `diskService`/`logService`/`themeService` 及主题管理测试，对应功能（终端日志、主题切换）当前未实现，已从用例中移除。

## 测试执行流程

### 本地开发测试

1. **运行所有测试**（当前 package.json 仅声明 `test` 脚本）
   ```bash
   npm run test
   # 或 bun test
   ```

> 注：原规范中的 `test:unit` / `test:integration` / `test:e2e` / `test:coverage` 脚本当前未在 package.json 中定义，待测试体系落地时补充。

### CI/CD 测试

1. **提交代码**
   - 代码提交时触发 GitHub Actions 工作流
   - 运行测试套件和代码质量检查

2. **Pull Request 测试**
   - 打开或更新 PR 时触发测试
   - 测试通过后才能合并

3. **发布前测试**
   - 发布新版本前运行完整测试套件
   - 确保所有测试通过

### 测试数据策略

- **模拟数据**: 使用模拟数据进行单元测试和集成测试
- **测试环境数据**: 为端到端测试准备测试环境数据

## 测试报告和监控

### 测试报告

- **覆盖率报告**: 生成代码覆盖率报告，标识未测试的代码
- **测试结果报告**: 详细的测试结果，包括通过、失败和跳过的测试
- **CI/CD 报告**: 在 GitHub Actions 中显示测试结果

### 测试监控

- **测试执行时间**: 监控测试执行时间，识别慢测试
- **测试失败率**: 监控测试失败率，及时发现问题
- **覆盖率趋势**: 跟踪覆盖率变化趋势，确保覆盖率目标达成

## 测试最佳实践

1. **测试命名规范**
   - 测试文件: `*.test.ts` 或 `*.spec.ts`
   - 测试套件: 描述测试的功能模块
   - 测试用例: 描述测试的具体场景

2. **测试编写技巧**
   - 使用描述性的测试名称
   - 每个测试用例只测试一个场景
   - 使用 beforeEach/afterEach 进行测试设置和清理
   - 避免测试中的重复代码

3. **测试维护**
   - 定期更新测试用例以反映需求变化
   - 修复失败的测试，不要忽略它们
   - 重构测试代码，保持其可维护性
   - 删除过时的测试用例

4. **测试与开发流程**
   - 采用测试驱动开发 (TDD) 方法
   - 在修复 bug 前先编写失败的测试
   - 在添加新功能前先编写测试用例
   - 将测试作为代码审查的一部分

## 常见测试问题及解决方案

### 测试缓慢

- **问题**: 测试执行时间过长
- **解决方案**: 
  - 识别并优化慢测试
  - 使用并行测试执行
  - 减少测试中的网络请求和文件操作

### 测试不稳定

- **问题**: 测试结果不一致，有时通过有时失败
- **解决方案**: 
  - 确保测试环境一致
  - 避免测试中的随机因素
  - 确保测试之间相互独立

### 测试覆盖率低

- **问题**: 代码覆盖率未达到目标
- **解决方案**: 
  - 识别未测试的代码区域
  - 为关键功能添加测试用例
  - 定期审查覆盖率报告

### 测试维护困难

- **问题**: 测试代码难以理解和维护
- **解决方案**: 
  - 遵循测试编写最佳实践
  - 重构测试代码，提高可读性
  - 添加测试注释，解释测试目的

## 结论

测试规范是确保 WinLink Migrator 项目质量和可靠性的关键组成部分。通过遵循本规范，开发团队可以构建更稳定、更可维护的应用程序，同时提高开发效率和代码质量。测试应被视为开发过程的重要组成部分，而不是事后考虑的事项。
