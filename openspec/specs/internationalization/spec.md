# 国际化规范

## 描述

国际化规范定义了 WinLink 项目的国际化实现方法、本地化规范与多语言支持策略。它确保应用程序能够轻松支持多种语言，为全球用户提供良好的用户体验。

> 当前实现：未使用 i18next 等第三方国际化库。所有翻译集中于单一文件 `src/translations.ts`，以 `zh` / `en` 两个对象组织翻译键，组件通过语言状态取值。下文"实际方案"部分描述当前做法，"通用指南"部分保留可复用的本地化规范建议。

## 国际化目标

1. **多语言支持**: 支持中文、英文
2. **本地化适配**: 适配不同地区的文化习惯和使用场景
3. **易于扩展**: 便于添加新的语言支持
4. **一致性**: 确保不同语言版本的用户体验一致
5. **性能优化**: 国际化实现不应显著影响应用性能

## 国际化架构

### 当前实际方案

- **单一翻译文件**: 全部文案集中在 `src/translations.ts`
- **双对象结构**: `zh`（默认）与 `en` 并列，键名一致
- **运行时切换**: `LanguageToggle` 组件切换当前语言状态；无第三方依赖
- **无回退机制**: 当前中英文键一一对应，未实现缺失键回退

### 目录结构（实际）

```
src/
├── translations.ts        # 中英文翻译键（zh / en 对象）
└── components/
    └── LanguageToggle.tsx # 语言切换组件
```

## 国际化实现指南

### 当前用法

1. **维护翻译键**（src/translations.ts）:
   ```typescript
   export const translations = {
     zh: { appTitle: 'WinLink', analyze: '分析安全性', /* ... */ },
     en: { appTitle: 'WinLink', analyze: 'Analyze Safety', /* ... */ },
   };
   ```

2. **在组件中取值**（示意）:
   ```tsx
   const t = (key: string) => translations[lang][key] ?? key;
   return <button>{t('analyze')}</button>;
   ```

3. **语言切换**:
   - `LanguageToggle` 在 `zh` / `en` 间切换并存入应用状态
   - 当前未持久化到 localStorage（如需持久化可后续补充）

> 注意：本仓库**未**引入 `i18next` / `react-i18next` 及 JSON 翻译目录，原方案中相关的安装、配置与组件示例不适用当前代码，已省略。

## 本地化规范

### 文本翻译规范

1. **翻译质量**: 
   - 准确传达原文含义
   - 符合目标语言的表达习惯
   - 保持专业术语的一致性

2. **格式规范**: 
   - 保持文本格式的一致性
   - 注意标点符号的使用
   - 确保日期、时间、数字等格式符合当地习惯

3. **长度考虑**: 
   - 不同语言的文本长度可能不同，UI 设计应考虑这一点
   - 避免使用固定宽度的容器容纳可能长度变化较大的文本

### 文化适配

1. **日期和时间格式**: 
   - 使用 `Intl.DateTimeFormat` 处理日期和时间格式化
   - 不同地区使用不同的日期和时间格式

2. **数字格式**: 
   - 使用 `Intl.NumberFormat` 处理数字格式化
   - 不同地区使用不同的数字分隔符

3. **货币格式**: 
   - 使用 `Intl.NumberFormat` 处理货币格式化
   - 不同地区使用不同的货币符号和格式

4. **度量单位**: 
   - 考虑不同地区使用的度量单位差异
   - 提供单位转换功能（如需要）

### 区域设置

1. **区域设置代码**: 
   - 使用标准的 BCP 47 语言标签，如 `en-US`、`zh-CN`
   - 主要语言标签在前，地区标签在后

2. **区域设置检测**: 
   - 应用启动时，检测用户的系统区域设置
   - 提供手动切换语言的选项

## 多语言支持策略

### 支持的语言

- **默认语言**: 中文 (`zh`)
- **主要语言**: 英文 (`en`)
- **未来计划支持的语言**: 可在 `translations.ts` 中追加对象（如 `ja`、`ko`、`es`、`fr`），并扩展切换组件

### 语言优先级

1. **用户选择的语言**（应用内切换）
2. **默认语言 (`zh`)**

### 语言包管理

1. **按需加载**: 对于大型应用，可以考虑按需加载语言包
2. **缓存策略**: 缓存已加载的语言包，避免重复加载
3. **更新机制**: 提供语言包的更新机制

## 翻译管理流程

### 翻译工作流

1. **提取可翻译文本**: 
   - 使用工具提取代码中的可翻译文本
   - 生成翻译模板文件

2. **翻译**: 
   - 由专业翻译人员或社区贡献者翻译
   - 使用翻译管理工具（如 Crowdin、Lokalise 等）

3. **集成翻译**: 
   - 将翻译文件集成到项目中
   - 验证翻译的正确性

4. **测试**: 
   - 测试不同语言版本的应用
   - 检查 UI 布局是否正确
   - 验证所有文本是否已翻译

### 翻译工具

1. **提取工具**: 
   - `i18next-parser`: 从代码中提取可翻译文本
   - `babel-plugin-i18next-extract`: Babel 插件，用于提取可翻译文本

2. **翻译管理工具**: 
   - **Crowdin**: 协作翻译管理平台
   - **Lokalise**: 本地化管理平台
   - **Transifex**: 全球化管理平台

3. **验证工具**: 
   - 自动化测试工具，检查翻译的完整性
   - 人工审查，确保翻译质量

### 翻译文件格式

- **JSON 格式**: 使用 JSON 格式存储翻译文本
- **结构化组织**: 按功能模块和组件组织翻译文本
- **注释**: 为复杂的翻译提供注释，帮助翻译人员理解上下文

## 性能优化

### 性能考虑

1. **翻译文件大小**: 
   - 优化翻译文件大小，避免冗余文本
   - 考虑使用压缩格式存储翻译文件

2. **加载性能**: 
   - 按需加载语言包
   - 缓存已加载的语言包
   - 预加载常用语言包

3. **运行时性能**: 
   - 使用 memoization 缓存翻译结果
   - 避免在渲染过程中频繁调用翻译函数

### 优化技术

1. **代码分割**: 
   - 将翻译文件与相应的功能模块一起打包
   - 实现按需加载

2. **缓存策略**: 
   - 使用浏览器缓存存储翻译文件
   - 使用内存缓存存储已加载的翻译

3. **懒加载**: 
   - 初始只加载默认语言
   - 其他语言在需要时加载

## 常见问题及解决方案

### 翻译缺失

- **问题**: 某些文本没有翻译
- **解决方案**: 
  - 确保所有可翻译文本都已提取
  - 实现默认语言回退机制
  - 定期检查翻译完整性

### UI 布局问题

- **问题**: 不同语言的文本长度不同，导致 UI 布局错乱
- **解决方案**: 
  - 使用弹性布局，避免固定宽度
  - 为文本容器设置合理的最小和最大宽度
  - 在设计阶段考虑文本长度变化

### 翻译不一致

- **问题**: 同一概念在不同地方的翻译不一致
- **解决方案**: 
  - 建立术语表，确保术语翻译一致
  - 使用翻译管理工具，统一管理翻译
  - 定期审查翻译，确保一致性

### 性能问题

- **问题**: 国际化实现影响应用性能
- **解决方案**: 
  - 实现按需加载语言包
  - 使用缓存策略
  - 优化翻译查找算法

### 日期和时间格式问题

- **问题**: 日期和时间格式不符合当地习惯
- **解决方案**: 
  - 使用 `Intl.DateTimeFormat` 处理日期和时间格式化
  - 测试不同地区的日期和时间显示

## 最佳实践

1. **使用语义化的翻译键**: 
   - 使用描述性的翻译键，避免使用硬编码的文本
   - 按功能模块组织翻译键

2. **提供上下文**: 
   - 为复杂的翻译提供上下文信息
   - 使用注释解释翻译的使用场景

3. **避免在翻译中使用 HTML**: 
   - 尽量避免在翻译文本中包含 HTML 标签
   - 如果必须使用 HTML，确保翻译人员了解其含义

4. **使用占位符**: 
   - 使用占位符处理动态内容，如 `{{name}}`
   - 避免在翻译中硬编码动态值

5. **测试所有语言**: 
   - 确保在所有支持的语言下测试应用
   - 检查不同语言下的用户体验

6. **文档化**: 
   - 为国际化实现提供详细的文档
   - 说明如何添加新的语言支持
   - 提供翻译指南

## 结论

国际化是 WinLink Migrator 项目的重要组成部分，它确保应用程序能够为全球用户提供良好的用户体验。通过遵循本规范，开发团队可以实现一个灵活、高效、易于维护的国际化系统。国际化实现不仅要考虑技术层面的问题，还要考虑文化和用户体验层面的问题，确保不同语言版本的应用程序都能为用户提供一致、优质的体验。
